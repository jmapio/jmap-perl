                      JMAP File Storage extension
                      draft-ietf-jmap-filenode-20

Abstract

   The JMAP base protocol (RFC 8620) provides the ability to upload and
   download arbitrary binary data.  This binary data is called a "blob",
   and can be used in all other JMAP extensions.

   This extension adds a FileNode data type and methods to expose blobs
   as a filesystem, along with the types of metadata that are provided
   by other remote filesystem protocols.

1.  Introduction

   JMAP ([JMAP-CORE] — JSON Meta Application Protocol) is a generic
   protocol for synchronizing data between a client and a server.  It is
   optimized for mobile and web environments, and aims to provide a
   consistent interface to different data types.

   In the same way that JMAP Calendars ([JMAP-CALENDARS]) replaces
   CalDAV ([CALDAV]) and JMAP Contacts ([JMAP-CONTACTS]) replaces
   CardDAV ([CARDDAV]), this document replaces the use of WebDAV
   ([WEBDAV]) for remote filesystem access.

2.  Addition to the Capabilities Object

   The capabilities object is returned as part of the JMAP Session
   object; see Section 2 of [JMAP-CORE].

   This document defines an additional capability URI.

2.1.  urn:ietf:params:jmap:filenode

   The capability urn:ietf:params:jmap:filenode being present in the
   "accountCapabilities" property of an account represents support for
   the FileNode data type.  Servers that include the capability in one
   or more "accountCapabilities" properties MUST also include the
   property in the "capabilities" property.

   The value of this property in the JMAP session "capabilities"
   property MUST be an empty object.

   The value of this property in an account's "accountCapabilities"
   property is an object that MUST contain the following information on
   server capabilities and permissions for that account:

   *  maxFileNodeDepth: "UnsignedInt|null"

      The maximum number of levels in the FileNode hierarchy, or null
      for no limit.  A FileNode may have at most one fewer ancestors
      than this value, so 1 allows only top-level nodes.

   *  maxSizeFileNodeName: "UnsignedInt"

      The maximum length, in (UTF-8) octets, allowed for the name of a
      FileNode.  This MUST be at least 100, although it is recommended
      servers allow more.

   *  forbiddenNameChars: "String|null"

      A string where each character is forbidden in FileNode names.  If
      null, the server does not restrict name characters beyond the
      requirement that names be non-empty Net-Unicode strings.  The
      server MUST reject names containing any of these characters with
      an "invalidProperties" error.

   *  supportedNodeTypes: "String[]"

      The @type values that the server allows clients to create in this
      account (see "FileNode Objects" below).  This MUST include
      "Directory" and "File".  It MAY include "SymLink" and any other
      value registered in the "JMAP FileNode Types" registry.  Clients
      MUST ignore values they do not recognize.

   *  fileNodeQuerySortOptions: "String[]"

      A list of all the values the server supports for the "property"
      field of the Comparator object in a "FileNode/query" sort (see
      "FileNode/query" below).  This MAY include properties the client
      does not recognize (for example, custom properties specified in a
      vendor extension).  Clients MUST ignore any unknown properties in
      the list.

   *  mayCreateTopLevelFileNode: "Boolean"

      If true, the user may create a FileNode (see "FileNode/set" below)
      in this account with a null parentId.  If false, creating a node
      with a null parentId, or moving one there, fails with "forbidden":
      the request is valid, but not allowed.  (Permission for creating a
      child of an existing FileNode is given by the "myRights" property
      on that FileNode.)

   *  webTrashUrl: "String|null"

      The URL at which the Directory with the "trash" role can be viewed
      on the web.  If null, there is no web URL available.

   *  caseInsensitiveNames: "Boolean"

      If true, the server treats node names as case-insensitive for all
      name collision checks, including the sibling uniqueness constraint
      and onExists handling.  The server preserves the original case as
      provided by the client.

   *  webUrlTemplate: "String|null"

      A template by which any node can be viewed on the web, in URI
      Template (level 1) format [URI-TEMPLATE].  The available variable
      is {id}, which is the FileNode id.  If null, there is no web URL
      available.

   *  webWriteUrlTemplate: "String|null"

      A URI Template (level 1) [URI-TEMPLATE] for writing content to a

3.  FileNode Data Type

   A FileNode is a set of metadata which behaves similarly to an inode
   in a filesystem.  In [WEBDAV] terminology a Directory corresponds to
   a collection and a File to a resource.

   The urn:ietf:params:jmap:filenode capability selects the FileNode
   data type and the methods defined below.

3.1.  FileNode Objects

   Every FileNode has a type, given by its @type property.  This
   document defines three types: "File", "Directory", and "SymLink".
   Each type has its own set of properties in addition to the properties
   common to all FileNodes.

   Properties that this document defines for one type MUST NOT appear on
   a FileNode of another type; they are omitted rather than set to null.
   An attempt to create or update a FileNode that sets a property not
   defined for its @type to a non-null value is an "invalidProperties"
   error.  The server MUST ignore a null value for such a property, both
   on create and on update.



Gondwana                   Expires 6 May 2027                   [Page 6]

Internet-Draft                JMAP FileNode                November 2026


   As in Section 5.3 of [JMAP-CORE], setting a property that has a
   default value to null, on create or update, sets it to that default,
   unless the property's description says otherwise.

   FileNode/get has additional rules for these properties (see
   "FileNode/get" below).  In particular, for a node the user can
   discover but not read, it returns null for most properties, even
   those whose type does not otherwise allow null (see "Access
   Control").

3.1.1.  Common Properties

   The following properties are defined for every FileNode, regardless
   of its type:

   *  @type: "String" (immutable)

      The type of the node.  Values are registered in the "JMAP FileNode
      Types" registry (see "IANA Considerations").  This document
      defines the values "File", "Directory", and "SymLink".  This MUST
      be provided on creation.  Attempting to change @type after
      creation is an "invalidProperties" error.  A server MUST reject
      the creation of a node with an @type that is not in the
      supportedNodeTypes capability with an "invalidProperties" error.
      Clients MUST be prepared to receive nodes with @type values they
      do not recognize, and SHOULD NOT interpret any of their properties
      other than the common properties.

   *  id: "Id" (immutable; server-set)

      The Id of the FileNode.

   *  parentId: "Id|null"

      The Id of the parent node, or null if this is a top-level node.
      The parent MUST be a node whose @type permits children; of the
      types defined in this document, only "Directory" does.  Setting
      parentId to any other node is an "invalidProperties" error.

   *  name: "String"











Gondwana                   Expires 6 May 2027                   [Page 7]

Internet-Draft                JMAP FileNode                November 2026


      User-visible name for the FileNode.  This MUST be a Net-Unicode
      string [UNICODE] of at least 1 character in length, subject to the
      maximum size given in the capability object.  There MUST NOT be
      two sibling FileNodes with both the same parent and the same name.
      The server MUST reject names containing any character listed in
      forbiddenNameChars with an "invalidProperties" error.  It MAY also
      reject other names it cannot store, such as "." and "..", in the
      same way.  See "Implementation Considerations" for guidance on
      which characters and names to forbid.

   *  created: "UTCDate" (default: current server time)

      The date the node was created.  The server never updates it
      automatically.

   *  modified: "UTCDate" (default: current server time)

      The date the content of the node was last modified.  The server
      updates it automatically only on a Direct HTTP Write.  See
      "Modification Timestamps" for usage guidance.

   *  accessed: "UTCDate" (default: current server time)

      The date the node was last accessed.  The server never updates it
      automatically.  Clients SHOULD provide an updated value when
      appropriate (see "Access Time Updates").

   *  changed: "UTCDate" (server-set)

      The date the server last recorded a change to a property of this
      node that has the same value for every user.  The server MUST
      automatically update this value whenever such a property is
      modified, including blobId, name, parentId, shareWith, executable,
      metadata, and the other mutable properties that are not per-user.
      This is not settable by clients.

      A change to a per-user property (isSubscribed, or privateMetadata
      (see "Extended Attributes and Named Streams")), or to the node's
      rights because of a change to an ancestor's shareWith or a move
      (see "Access Control"), need not update changed.  The server
      SHOULD report a per-user change in FileNode/changes only to the
      users whose value changed.  It MAY instead update changed, and
      report the node in FileNode/changes to other users too, when it
      cannot efficiently determine which users are affected, such as
      when the value is held for a group.

3.1.2.  Container Properties

   The following properties are defined for every FileNode whose @type
   permits children; of the types defined in this document, only
   "Directory" does.  They do not appear on other nodes, whose rights
   come from their parent (see "Access Control").

   *  isSubscribed: "Boolean" (default: true)

      This property is stored per user, and if true, the node should be
      displayed to the current user.  Setting it changes only the
      current user's value, and requires no rights beyond being able to
      discover the node.

   *  myRights: "FilesRights" (server-set)

      The set of rights the user has on this node.  A *FilesRights*
      object has the following properties:

      -  mayRead: Boolean The user may read all properties and the blob
         content of this node.  Without it, some properties are still
         visible (see "Access Control").

      -  mayAddChildren: Boolean The user may create child nodes in this
         directory, or move nodes into it.

      -  mayRename: Boolean The user may rename or move this node, or
         change its role.

      -  mayDelete: Boolean The user may destroy this node.

      -  mayModifyContent: Boolean The user may update the content-
         related properties of this node (blobId, mediaType, target,
         created, modified, accessed, executable).

      -  mayShare: Boolean The user may change the sharing of this node
         (see [JMAP-SHARING]).

   *  shareWith: "Id[FilesRights]|null"

      A map of userId to rights for users this node is shared with.
      This is the access control list set on this node only; rights
      inherited from ancestors do not appear in it (see "Access
      Control").  The owner of the node MUST NOT be in this set.  This
      is null if the user requesting the object does not have
      myRights.mayShare, or if the node is not shared with anyone.

3.1.3.  File Properties

   A FileNode with @type "File" is a regular file with blob content.  In
   addition to the common properties, it has the following properties:

   *  blobId: "Id"

      The blobId for the content of this file.  This MUST be provided on
      creation, including for zero byte files.  Setting blobId to null
      is an "invalidProperties" error.  Updating the blobId replaces the
      file's content; the server MUST update size to match the new blob.
      A blob referenced by a FileNode MUST NOT be expired or garbage
      collected by the server while the FileNode exists.

   *  size: "UnsignedInt" (server-set)

      The size in bytes of the associated blob data.  Size is optional
      on create and update, but if provided it MUST match the size of
      the provided blobId.  If the client updates blobId without
      providing size, the server sets size from the new blob and returns
      the size in the "updated" response.

   *  mediaType: "String" (default: "application/octet-stream")

      The media type of the file.  If not provided on creation, or if
      set to null, the server sets it to "application/octet-stream".
      Values are normally those registered in the IANA media-types
      registry, but servers MUST NOT reject media types that are not
      recognized.  Servers MUST reject media types if the value does not
      conform to the ABNF of Section 4.2 of [MEDIA-TYPES].

   *  executable: "Boolean" (default: false)

      If true, the file should be treated as an executable by operating
      systems that support this flag.

3.1.4.  Directory Properties

   A FileNode with @type "Directory" is a collection that may contain
   child nodes.  In addition to the common properties, it has the
   following property:

   *  role: "String|null" (default: null)

      An indication that this directory has a special role.  A directory
      with the "root" role should have a null parentId.  Clients MUST
      ignore unrecognized role values.  Values are registered in the
      "JMAP FileNode Roles" registry (see IANA Considerations).



Gondwana                   Expires 6 May 2027                  [Page 10]

Internet-Draft                JMAP FileNode                November 2026


      A client may set role on create or update, and may set it to null
      to clear it.  Changing role on an existing node requires mayRename
      on that node.  At most one Directory in an account has a given
      role; setting a role that another Directory already has is an
      "invalidProperties" error.  As for sibling names, the server
      checks this against the result of all the creates, updates and
      destroys in a FileNode/set together, so a client can move a role
      from one Directory to another in a single method.  A server MAY
      reject setting or clearing a role for policy reasons with
      "forbidden": for example, a role that it manages itself, such as
      "root" or "trash", or a role that it allows only on a top-level
      Directory or within a limited depth of the tree.

3.1.5.  SymLink Properties

   A FileNode with @type "SymLink" is a symbolic link to another path in
   the tree.  In addition to the common properties, it has the following
   property:

   *  target: "String[]"

      The target path of the symlink, as an array of path elements.
      Each element is a node name in the path.  An empty string as the
      first element indicates an absolute path from the root of the
      tree; otherwise the path is relative to the symlink's parent.  An
      element of ".." refers to the parent directory.  The root of the
      tree is the set of nodes with a null parentId, not a Directory
      with the "root" role.  A relative target on a node with a null
      parentId resolves from the root, and a ".." element at the root
      does not resolve.  The target is not required to resolve to an
      existing node (symlinks may dangle).  The target is mutable;
      updating it changes where the symlink points.  This MUST be
      provided on creation.  Setting target to null is an
      "invalidProperties" error.

3.2.  FileNode Methods

3.2.1.  FileNode/get

   This is a standard Foo/get method, with the following differences:

   *  The @type property is always returned, even if it is not included
      in the properties argument.

   *  If the properties argument includes a property that is defined for
      some FileNode type but not for a node's @type, the server omits
      that property from that node in the response.  It does not return
      the property with a null value.

   *  For a node the user can discover but not read, the server returns
      null for most properties (see "Access Control").

   There is one additional request argument:

   *  fetchParents: "Boolean" (default: false)




Gondwana                   Expires 6 May 2027                  [Page 12]

Internet-Draft                JMAP FileNode                November 2026


      If true, the server returns all ancestor nodes of the requested
      ids, as additional entries in the list array.  Each node appears
      in the list only once.

3.2.2.  FileNode/changes

   This is a standard Foo/changes method.  A node can be reported as
   changed without any change to its own properties: see changed for
   per-user properties, and "Access Control" for changes to a node's
   rights or discoverability.

3.2.3.  FileNode/set

   This is a standard Foo/set method, with the following differences:

   An attempt to move a node beneath itself is rejected with an
   "invalidProperties" error.

   Within a single FileNode/set, the server MUST check the uniqueness of
   sibling names against the result of all its creates, updates and
   destroys together, so that a client can destroy a node and create its
   replacement in the same method.

   There are these additional top-level arguments:

   *  onDestroyRemoveChildren: "Boolean" (default: false)

      If false, an attempt to destroy a FileNode that has children is
      rejected with a "nodeHasChildren" error.  If all the children are
      destroyed in the same method, the server MUST NOT return this
      error: it either destroys children before their parents, or checks
      this constraint only against the final state.

      If true, destroying a node also destroys all its descendants, and
      the server MUST include the ids of all of them in the "destroyed"
      list of the response.

   *  onExists: "String|null" (default: null)

      Controls what happens when a create or update would give a
      FileNode the same name as an existing sibling.

      If null, the server rejects the create or update with an
      "alreadyExists" error.







Gondwana                   Expires 6 May 2027                  [Page 13]

Internet-Draft                JMAP FileNode                November 2026


      If "replace", the server destroys the existing node, and MUST
      include its id, and the ids of any descendants destroyed with it,
      in the "destroyed" list of the response.  A node of any @type may
      replace a node of any other @type.

      If "rename", the server changes the "name" property so that it
      does not clash, using an algorithm of its choice, and MUST include
      the new name in the "created" or "updated" entry for that id.

      Any other value is rejected with an "invalidArguments" error.

      "replace" destroys whichever node holds the name when the method
      runs.  To replace only the node it expects, a client instead
      destroys that node and creates the new one in the same FileNode/
      set, with an "ifUnchangedBy" precondition ([JMAP-CONDITIONAL]) on
      the node it destroys.

      For "replace", the server makes these checks in order, and stops
      at the first that fails:

      1.  If the existing node is not discoverable by the user (see
          "Access Control"), the operation fails with "forbidden", and
          the server MUST NOT destroy that node or reveal its id.
          Servers may also return "forbidden" for other reasons, such as
          a file name policy, so the error does not confirm that the
          name is taken.

      2.  If the user does not have mayDelete on the existing node, the
          operation fails with "forbidden".

      3.  If the existing node has children, the operation fails with
          "nodeHasChildren" if onDestroyRemoveChildren is false, or with
          "forbidden" if replacing it would remove nodes the user cannot
          discover (see "Access Control").

      "rename" applies whether or not the user can discover the existing
      node.

   *  compareCaseInsensitively: "Boolean" (default: false)

      If true, name collision checks (including onExists handling) treat
      names as case-insensitive for this request.  This has no effect if
      the server already has caseInsensitiveNames set to true in its
      capability.  See "Case Sensitivity" for its use.

   Errors (in addition to standard SetError codes from [JMAP-CORE]):





Gondwana                   Expires 6 May 2027                  [Page 14]

Internet-Draft                JMAP FileNode                November 2026


   *  "alreadyExists" — a create or update would cause a name collision
      with a discoverable sibling FileNode, and onExists did not resolve
      it.  The SetError object MUST include an existingId property with
      the id of the existing FileNode.

   *  "forbidden" — among other cases: a name collision with a sibling
      the user cannot discover; an onExists replacement without the
      required rights on the existing node (see onExists above); a
      destroy that would remove nodes the user cannot discover; a
      rename, move, role change or destroy without the rights it needs,
      or a rename, move or destroy of a Directory with a role; a change
      to a role that server policy does not allow; or a create or move
      to the top level without mayCreateTopLevelFileNode (see "Access
      Control").

   *  "invalidProperties" — among other cases: an attempt to move a node
      to a descendant of itself, creating a cycle in the tree, to make a
      node the child of a node whose @type does not permit children, to
      change the @type of a node, to set a property that is not defined
      for the node's @type to a non-null value, to give a Directory a
      role that another Directory in the account already has, or a
      create or move that would give the node, or any of its
      descendants, more ancestors than maxFileNodeDepth allows.

   *  "nodeHasChildren" — a destroy or onExists replacement of a
      FileNode that has children, with onDestroyRemoveChildren false.

3.2.4.  FileNode/copy

   This is a standard Foo/copy method with the same additional top-level
   arguments as FileNode/set (onDestroyRemoveChildren, onExists, and
   compareCaseInsensitively), with the same behavior.  These arguments
   apply to the nodes created and replaced in the destination account.

   Each copy is a new node, with a new id and a new changed value.  It
   has the same created, modified and accessed values as its original,
   unless the client gives others.  For a File, the server copies the
   content of its blob into the destination account; the blob need not
   already exist there, and the new blobId may differ.  shareWith and
   role are not copied, even within one account: the copy takes its
   rights from its new parent, and isSubscribed takes its default value.
   metadata and privateMetadata are copied as [JMAP-METADATA] describes.









Gondwana                   Expires 6 May 2027                  [Page 15]

Internet-Draft                JMAP FileNode                November 2026


   Copying a Directory copies its whole subtree: each descendant is
   copied, by the rules above and with the same name, beneath the copy
   of its parent.  The copy of a Directory and all its descendants
   succeeds or fails as a whole; if the destination cannot hold any
   descendant (for example, a SymLink where "SymLink" is not in
   supportedNodeTypes), the copy fails.

   Copying a node requires mayRead on it and mayAddChildren on the
   destination parent (or mayCreateTopLevelFileNode).  The response
   gives only the id of the new Directory; FileNode/query with an
   ancestorId condition finds the copied descendants.

   If onSuccessDestroyOriginal is true, the implicit FileNode/set call
   that destroys the originals (Section 5.4 of [JMAP-CORE]) has
   onDestroyRemoveChildren true.  A client that must not lose a node
   added to the tree between the copy and the destroy passes
   destroyFromIfInState.

   Unlike other Foo/copy methods (Section 5.4 of [JMAP-CORE]), FileNode/
   copy allows accountId to be the same as fromAccountId, so a client
   can copy a node or a tree within one account.  An attempt to copy a
   Directory into itself or one of its descendants is rejected with
   "invalidProperties".

   The response has one additional property:

   *  destroyed: "Id[]|null"

      The ids of the FileNodes in the destination account that were
      destroyed because onExists replaced them, including any
      descendants removed with onDestroyRemoveChildren.  This is null if
      no FileNodes were destroyed.

   Errors: the same additional errors as FileNode/set apply.

3.2.5.  FileNode/query

   This is a standard Foo/query method except for the following:

   There is one additional request argument:

   *  depth: "UnsignedInt|null" (default: null)









Gondwana                   Expires 6 May 2027                  [Page 16]

Internet-Draft                JMAP FileNode                November 2026


      The maximum depth in the tree, counted from the top level, at
      which a node can match: nodes with a null parentId are at depth 0,
      their children at depth 1, and so on.  This applies whatever the
      filter; conditions such as parentId and ancestorId only select
      among the nodes within it, and depth is never counted from them.
      So ancestorId without depth matches the whole subtree.  If null,
      there is no limit.

   The following filter criteria are defined:

   *  isTopLevel: "Boolean"

      If true, the node must have a null parentId to match the
      condition.

   *  parentId: "Id"

      A FileNode id.  A node must have a parentId equal to this to match
      the condition.

   *  ancestorId: "Id"

      A FileNode id.  A node must have an ancestor (parent, parent of
      parent, etc.) with an id equal to this to match the condition.

   *  descendantId: "Id"

      A FileNode id.  A node must be an ancestor (parent, parent of
      parent, etc.) of the node with this id to match the condition.
      This is the inverse of ancestorId.

   *  nodeType: "String"

      A node type value.  Only nodes whose @type is precisely this value
      match this condition.  This filter, and the nodeType sort property
      below, are named nodeType rather than @type; they operate on the
      @type property.

   *  role: "String"

      A role name.  Only nodes with precisely this role match this
      condition.

   *  hasAnyRole: "Boolean"

      If true, any node with a defined role matches this condition.  If
      false, any node which has a role does not match this condition.




Gondwana                   Expires 6 May 2027                  [Page 17]

Internet-Draft                JMAP FileNode                November 2026


   *  blobId: "Id"

      A FileNode must have a blobId equal to this to match the
      condition.

   *  isExecutable: "Boolean"

      If true, the FileNode must have a true executable value.

   *  createdBefore: "UTCDate"

      The creation date of the node must be before this date to match
      the condition.

   *  createdAfter: "UTCDate"

      The creation date of the node must be on or after this date to
      match the condition.

   *  modifiedBefore: "UTCDate"

      The modified date of the node must be before this date to match
      the condition.

   *  modifiedAfter: "UTCDate"

      The modified date of the node must be on or after this date to
      match the condition.

   *  accessedBefore: "UTCDate"

      The accessed date of the node must be before this date to match
      the condition.

   *  accessedAfter: "UTCDate"

      The accessed date of the node must be on or after this date to
      match the condition.

   *  minSize: "UnsignedInt"

      The size of the node in bytes must be equal to or greater than
      this number to match the condition.

   *  maxSize: "UnsignedInt"

      The size of the node in bytes must be less than this number to
      match the condition.



Gondwana                   Expires 6 May 2027                  [Page 18]

Internet-Draft                JMAP FileNode                November 2026


   *  name: "String"

      A FileNode must have exactly the same octets in its name property
      to match the condition.

   *  nameMatch: "String"

      Matches the _name_ property of the node using glob syntax.  The
      following special patterns are defined: * matches any sequence of
      characters, ? matches any single character, and a pair of brackets
      matches any single character in the bracketed set (for example,
      [abc] matches "a", "b", or "c"; [a-z] matches any letter from "a"
      to "z"; [!abc] or [^abc] matches any character not in the set).
      All other characters match literally.  The match is case-
      insensitive.

   *  mediaType: "String"

      A FileNode must have exactly the same octets in its mediaType
      property to match the condition.

   *  mediaTypeMatch: "String"

      Matches the _mediaType_ property of the node using the same glob
      syntax as _nameMatch_.

   *  body: "String"

      Match the content of the referenced blob, see the definition of
      _body_ in Section 4.4.1 of [JMAP-MAIL].  The server may use any
      technology to extract meaningful text from the blob for searching,
      or interpret the string in any way, to choose the nodes that it
      believes the user wants to see.

   *  text: "String"

      Matches a node if the _body_ condition with this value matches, or
      if its name or mediaType contains this value, compared case-
      insensitively.

   The blobId, isExecutable, minSize, maxSize, mediaType,
   mediaTypeMatch, and body conditions match only nodes whose @type is
   "File".  The role and hasAnyRole conditions match only nodes whose
   @type is "Directory".  This applies to both true and false values.
   For example, a hasAnyRole condition of false matches only Directories
   without a role, and an isExecutable condition of false matches only
   Files that are not executable.




Gondwana                   Expires 6 May 2027                  [Page 19]

Internet-Draft                JMAP FileNode                November 2026


   For a node the user can discover but not read, a condition on a
   property that FileNode/get returns as null for that node (see "Access
   Control") does not match the node, whatever its value.  The body
   condition, and the body part of the text condition, never match such
   a node.

   It also supports the following additional sort properties:

   *  tree:

      Sort by tree; which means by name, but any Directory node is
      immediately followed by the recursive application of the same sort
      to its child nodes.  This is similar to the output of the find
      command on a filesystem.

   *  nodeType:

      Sort by @type.  Directories sort first, then symlinks, then files,
      then nodes of any other @type ordered by the @type value.

   When sorting by a property that is not defined for a node's @type
   (for example size on a Directory), or that FileNode/get returns as
   null because the user cannot read the node (see "Access Control"),
   nodes without the property sort before nodes that have it when
   isAscending is true.  Nodes that lack the property are ordered among
   themselves as if that Comparator were absent from the sort.

4.  Direct HTTP Write

   When the server advertises a webWriteUrlTemplate, clients can update
   the content of a File directly via HTTP without using FileNode/set.
   The URL is constructed by expanding the template with the FileNode
   id.  This is only valid for nodes with @type "File"; requests
   targeting any other type of node MUST be rejected with 400 (Bad
   Request).  A request for a node that does not exist, or that the user
   cannot discover, MUST be rejected with 404 (Not Found).

   The user MUST have mayModifyContent on the node, which for a File is
   in its parent's myRights (see "Access Control").  Requests without it
   MUST be rejected with 403 (Forbidden).  Authentication uses the same
   mechanism as other JMAP HTTP endpoints.





Gondwana                   Expires 6 May 2027                  [Page 20]

Internet-Draft                JMAP FileNode                November 2026


   A request that would take the account over its quota (see "Quotas")
   MUST be rejected with 507 (Insufficient Storage) (Section 11.5 of
   [WEBDAV]).  Whenever the server rejects a request, with this or any
   other status, it MUST NOT change the node.

4.1.  Preventing Lost Updates

   The server assigns a strong entity tag (Section 8.8.3 of [HTTP]) to a
   File's content at the write URL, which changes whenever the content
   does.  On success, the server MUST include an ETag header field with
   the new entity tag in the response to a PUT or PATCH.  The server can
   use any value with the properties of a strong entity tag.  It is
   RECOMMENDED that the server use the node's current blobId as the
   opaque value (for example, "Bfa61c0" for a node with blobId
   "Bfa61c0"), so that clients can form it from FileNode/get.

   The server MUST support If-Match (Section 13.1.1 of [HTTP]) on PUT
   and PATCH.  If the condition is false, the server MUST respond with
   412 (Precondition Failed).  A client SHOULD send If-Match on every
   PATCH, and on a PUT unless it intends to overwrite whatever content
   the node has.

4.2.  PUT

   A PUT request replaces the entire content of the node.  The request
   body is the new content.  The type and subtype of the Content-Type
   header field set the mediaType of the node; the server does not store
   any parameters (such as "charset").  If the request has no Content-
   Type header field, the server sets mediaType to "application/octet-
   stream".  If the Content-Type header field does not conform to the
   ABNF of Section 8.3 of [HTTP], the server MUST respond with 400 (Bad
   Request).

   On success, the server MUST update the node's blobId, size, and
   mediaType properties, and set modified to the current server time (a
   PUT cannot carry a client timestamp; a client that wants a different
   one sets it with FileNode/set afterwards).  It returns 200 (OK) with
   a JSON body:

   {
     "blobId": "Bnewblob123",
     "size": 48576,
     "mediaType": "text/plain"
   }







Gondwana                   Expires 6 May 2027                  [Page 21]

Internet-Draft                JMAP FileNode                November 2026


4.3.  PATCH

   A PATCH request applies a partial modification to the node's current
   content.  The Content-Type of the request indicates the patch format.
   The supported patch formats are those listed in the
   supportedPatchTypes capability of [JMAP-BLOBEXT] (for example,
   application/x-rdiff-delta, application/x-bsdiff, text/x-diff).  The
   server applies the delta to the node's current blob to produce the
   new content.

   On success, the server MUST update the node's blobId and size
   properties, and set modified to the current server time, as for PUT.
   The server MUST NOT change the node's mediaType.  A client that needs
   to change it uses PUT, or updates mediaType with FileNode/set.  The
   response is 200 (OK) with the same JSON body as PUT:

   {
     "blobId": "Bpatched456",
     "size": 49152,
     "mediaType": "text/plain"
   }

   Errors in applying a patch are handled as described in Section 2.2 of
   [HTTP-PATCH].  In particular, the server MUST respond with 415
   (Unsupported Media Type) for a patch format it does not support, 400
   (Bad Request) for a malformed patch, and 409 (Conflict) for a patch
   that cannot be applied to the node's current content.

4.4.  Integrity

   A PUT or PATCH request MAY carry Repr-Digest or Content-Digest header
   fields [DIGEST-FIELDS] for the data it sends: for PUT, the new
   content of the node; for PATCH, the patch.  The server MUST verify
   each digest whose algorithm it supports.  If any does not match, the
   server MUST respond with 400 (Bad Request).  As [DIGEST-FIELDS]
   describes, a digest whose algorithm the server does not support is
   ignored.  The algorithms a server supports are those in the
   supportedDigestAlgorithms capability of [JMAP-BLOBEXT], which lists
   them in the server's order of preference; clients SHOULD use the
   first one they support.











Gondwana                   Expires 6 May 2027                  [Page 22]

Internet-Draft                JMAP FileNode                November 2026


   A client can ask for a digest of the node's new content by sending
   Want-Repr-Digest [DIGEST-FIELDS].  On success, for each algorithm it
   lists that the server supports, the server SHOULD include a member
   named "digest:" followed by the algorithm name (for example
   "digest:sha-256") in the JSON response body, holding the
   base64-encoded digest of the node's new content, as Blob/get does in
   [JMAP-BLOBEXT].  The digest is in the body because any digest header
   fields on the response describe the response body itself, not the
   node.

   {
     "blobId": "Bpatched456",
     "size": 49152,
     "mediaType": "text/plain",
     "digest:sha-256": "lu2dEm1cr1Hg2GqVDXMTGP3sgQfFYyp8XUd2ZTgp5Qc="
   }

5.  Access Control

   Access control lists are set with shareWith, which only nodes whose
   @type permits children can have.  Rights are inherited down the tree:
   a node's myRights is the union of the rights granted to the user by
   the shareWith entries on the node and on all its ancestors.
   Inherited rights are a floor.  A shareWith entry on a descendant can
   grant a user more rights on that subtree, but it cannot take away
   rights granted higher up.

   A node whose @type does not permit children has no myRights.  The
   user's rights on it are those in its parent's myRights;
   mayAddChildren and mayShare do not apply to it.  Such a node with a
   null parentId is discoverable only by the account owner, who has all
   rights on it.

   Nodes which are not "discoverable" MUST be reported in notFound if
   fetched with FileNode/get and MUST NOT be returned in response to
   FileNode/query.  Nodes are discoverable in one of two ways:

   1.  If the node or an ancestor of the node has mayRead true.

   2.  If the node or a descendant of the node has a shareWith entry
       that grants the user any right.

   A node that is discoverable only through the second rule has mayRead
   false.  A query with that node as the parent returns only those of
   its children that are themselves discoverable.






Gondwana                   Expires 6 May 2027                  [Page 23]

Internet-Draft                JMAP FileNode                November 2026


   For a node that is discoverable but does not have mayRead, FileNode/
   get returns the real values of id, @type, name, parentId, myRights,
   isSubscribed, and shareWith (which follows its own rule for
   mayShare).  It returns null for every other property defined for the
   node's @type, including created, changed, and role, even where that
   property's type does not otherwise allow null.  A change to a
   property the user sees as null is not visible to the user, so the
   server SHOULD NOT report the node as updated in FileNode/changes
   because of it, but MAY do so if it cannot efficiently determine
   whether any property visible to the user changed.

   Such a node can have descendants the user cannot discover.  A destroy
   that would remove any of them, either through onDestroyRemoveChildren
   or as part of a node replaced through onExists, MUST be rejected with
   "forbidden", and the server MUST NOT destroy any node in that
   subtree.  Without onDestroyRemoveChildren, destroying such a node
   while it has children fails with "nodeHasChildren" whether or not the
   user can discover those children.

   This leads to a sharee seeing the full path to anything that they
   have access to, but nothing else.

   For example, in a Unix home directory layout where Alice has shared
   her "forBob" directory, Bob might see:

   /home
     /alice
       /shared
         /forBob
           file1.jpg
           file2.txt
           ...
     /bob
       bobfile.txt
       ...

   Alice sees many more files and directories under "/home".

   To rename or move a node, or change its role, the server checks
   mayRename, and to destroy it mayDelete, in the rights of the node
   itself; for a node with no myRights, these are its parent's rights.
   Moving a node also requires mayAddChildren on the new parent, or
   mayCreateTopLevelFileNode to move it to the top level.  Without these
   rights, the operation fails with "forbidden".

   A Directory with a role cannot be destroyed, renamed or moved; the
   server rejects any attempt with "forbidden".  This does not change
   the rights it reports in myRights, which its children with no



Gondwana                   Expires 6 May 2027                  [Page 24]

Internet-Draft                JMAP FileNode                November 2026


   myRights of their own take as theirs: files in a directory with the
   "trash" role, for example, can still be destroyed.  A client that
   needs to destroy, rename or move such a Directory first clears its
   role (see "role" in "Directory Properties").

   A node's rights can change without any change to the node itself:
   through a change to shareWith on an ancestor, or when the node or an
   ancestor moves to a parent whose inherited rights differ.  The server
   MUST report every node whose rights for a user changed as changed in
   FileNode/changes for that user, including nodes that have no myRights
   of their own and take their rights from their parent.

   Otherwise, moving or renaming a node changes only that node.  Its
   descendants keep all their properties (their path is not a property),
   so the server does not report them in FileNode/changes unless their
   rights changed.

   When a node stops being discoverable by the user, for example because
   a shareWith entry was removed or the node was moved out of a shared
   Directory, the server reports it as destroyed in FileNode/changes.

   Sharing can make large changes to the set of nodes a user can see:
   when Alice first shared that directory, Bob would have been told of a
   large number of new nodes in response to a FileNode/changes query.
   The server might report these as "created" or "updated" — it is not
   always possible for the server to know whether a node was previously
   visible to the user.

6.  Quotas

   Servers that support JMAP Quotas ([JMAP-QUOTAS]) SHOULD provide Quota
   objects with "FileNode" in the types array.  Both the octets resource
   type (total storage used by FileNode blobs) and the count resource
   type (number of FileNode objects) are applicable.

7.  Integration with JMAP Blob Extensions

   When a server advertises both urn:ietf:params:jmap:filenode and
   urn:ietf:params:jmap:blob2, the ArchiveEntry object type (defined in
   [JMAP-BLOBEXT]) is extended with two additional properties:

   *  nodeId: "Id|null"

      A FileNode id.  When present, the server populates the archive
      entry from the referenced FileNode's properties.  The blobId,
      name, created, and modified are taken from the FileNode.  The
      user's rights on the FileNode (specifically the mayModifyContent
      right) and, for a File, the executable property inform the mode



Gondwana                   Expires 6 May 2027                  [Page 25]

Internet-Draft                JMAP FileNode                November 2026


      field in the archive entry (for example, permissions and
      executable bit).  If the ArchiveEntry also provides explicit
      values for any of these properties, the explicit values take
      precedence.  Mutually exclusive with providing blobId directly
      when the FileNode's @type is "File".

   *  recurse: "Boolean" (default: false)

      Only valid when the referenced FileNode's @type is "Directory".
      When true, the server recursively includes all children of the
      directory in the archive.  Each descendant's name is the name of
      the referencing entry followed by its path relative to the
      directory.  Directory names MUST include a trailing /.

   A FileNode with @type "SymLink", whether referenced directly by
   nodeId or reached by recurse, is added to the archive as an entry
   with entryType "symlink".  The server never follows the symlink.  The
   entry's linkTarget is the elements of the SymLink's target joined
   with "/".  An absolute target, whose first element is the empty
   string, therefore produces a linkTarget that starts with "/".

   Some archive formats cannot hold every node type.  For example,
   "application/zip" has no symlink entries.  The ArchiveRecipe (defined
   in [JMAP-BLOBEXT]) is extended with one additional property that
   controls how the server handles such nodes:

   *  onUnsupportedEntry: "String" (default: "error")

      This applies to any node, referenced by nodeId or reached by
      recurse, that the archive format cannot represent.  If "error",
      the server rejects the Blob/convert creation with an
      "unsupportedEntry" SetError, and creates no archive.  If "skip",
      the server leaves such nodes out of the archive.  Any other value
      is an "invalidProperties" error.

   This property applies only to entries that the server builds from
   FileNodes.  An entry that the client gives in full, with an
   unsupported entryType, is still an "invalidProperties" error as
   [JMAP-BLOBEXT] requires.

   If nodeId references a FileNode that the user does not have
   permission to read, or that does not exist, the server MUST reject
   the Blob/convert creation with a "notFound" SetError.

7.2.  Extracting Archives into FileNodes

   When both capabilities are present, the ExtractRecipe (defined in
   [JMAP-BLOBEXT]) is extended with the following additional properties:

   *  parentNodeId: "Id|null"




Gondwana                   Expires 6 May 2027                  [Page 27]

Internet-Draft                JMAP FileNode                November 2026


      The id of a FileNode with @type "Directory".  When present, the
      server extracts the archive contents into this directory, creating
      FileNode objects for each entry.  Subdirectories in the archive
      are created as FileNodes with @type "Directory".  File entries
      become FileNodes with @type "File" and their blobId set to the
      extracted content.  The FileNode's created and modified are taken
      from the archive entry's, when it has them.  If the archive entry
      includes a mode field, the server SHOULD use it to set the
      executable property on the created FileNode.

      Symlink entries become FileNodes with @type "SymLink" if "SymLink"
      is in the supportedNodeTypes capability.  The server splits the
      entry's linkTarget on "/" to produce the target path elements.  A
      linkTarget that starts with "/" produces an empty string as the
      first element, which marks an absolute path.  The server drops any
      other empty elements.

      An entry is unsupported if the server cannot create a FileNode for
      it.  These are symlink entries when "SymLink" is not in
      supportedNodeTypes, and entries of any type that has no FileNode
      equivalent ("hardlink", "fifo", "blockDevice", and "charDevice").
      The server splits each entry's name on "/" into path components.
      It treats every name as relative to parentNodeId: it ignores any
      leading "/" and the trailing "/" of a directory entry, and drops
      any "." component, so "/docs/", "./docs/" and "docs/" all name the
      same directory.  An entry is also unsupported if its name contains
      a ".." component or an empty component (as in "docs//readme.txt"),
      or would produce a name or depth that the server would reject in
      FileNode/set.  The onUnsupportedEntry property controls how the
      server handles them.

   *  onUnsupportedEntry: "String" (default: "error")

      If "error", the server rejects the Blob/convert creation with an
      "unsupportedEntry" SetError, and creates no FileNodes.  If "skip",
      the server does not create a FileNode for an unsupported entry,
      and extracts the other entries as usual.  A skipped entry still
      appears in the response entries array, with a null nodeId.  Any
      other value is an "invalidProperties" error.

   *  onExists: "String|null" (default: null)

      Controls the behavior when an extracted entry would collide with
      an existing FileNode name under the same parent.  The values and
      semantics are the same as for FileNode/set (see above): null
      rejects with an "alreadyExists" SetError, "replace" destroys the
      existing node, and "rename" gives the new node a server-chosen
      name.



Gondwana                   Expires 6 May 2027                  [Page 28]

Internet-Draft                JMAP FileNode                November 2026


      A directory entry that collides with an existing Directory the
      user can discover does not use onExists: the server merges the
      entry into the existing Directory.  It creates no new node for
      that entry, leaves the existing Directory's properties unchanged,
      and extracts the entries beneath it into the existing Directory,
      where their own collisions are handled in the same way.  Adding a
      node to an existing Directory requires mayAddChildren on it, as
      for FileNode/set.

      onExists applies to every other collision: a file or symlink entry
      with any existing node, or a directory entry with an existing node
      that is not a Directory.  When "rename" renames a directory entry,
      the entries beneath it are extracted into the renamed Directory.
      The extraction has no equivalent of onDestroyRemoveChildren, so
      "replace" of an existing node that has children fails with
      "nodeHasChildren".

   If extraction fails for any reason, the server rejects the Blob/
   convert creation with the SetError for that failure (for example
   "alreadyExists", "forbidden", "nodeHasChildren", or
   "unsupportedEntry"), and MUST NOT create, destroy or change any
   FileNode.  An extraction either succeeds as a whole or has no effect.

   When parentNodeId is set, each ArchiveEntry in the response entries
   array includes an additional nodeId property containing the id of the
   FileNode that was created for that entry, the id of the existing
   Directory for a directory entry that was merged into it, or null if
   the server skipped the entry.

   If parentNodeId references a FileNode that does not exist, is not a
   Directory, or for which the user does not have mayAddChildren
   permission, the server MUST reject the Blob/convert creation with an
   appropriate SetError ("notFound", "invalidProperties", or
   "forbidden").

8.  Extended Attributes and Named Streams

   Operating systems associate named side-channel data with files: POSIX
   extended attributes (getxattr/setxattr), macOS extended attributes
   (including Finder tags and the quarantine flag) and resource forks,
   NTFS and SMB2 alternate data streams, and NFSv4 named attributes.  A
   FileNode carries these using the JMAP Object Metadata extension
   ([JMAP-METADATA]).  A server that supports named attributes on
   FileNodes lists "FileNode" in the "dataTypes" of its
   urn:ietf:params:jmap:metadata capability.  Clients then read and
   write the attributes through the "metadata" property, and through the
   "privateMetadata" property where the server sets supportsPrivate.
   That extension adds both properties to the FileNode object, on
   FileNodes of every @type.

8.1.  The "xattr" Namespace

   This document defines the "xattr" namespace for the "metadata" and
   "privateMetadata" properties.  Its value is an object mapping an
   attribute name to the attribute's value.  The attribute name is the
   platform-native name of the attribute or stream, stored verbatim (for
   example "user.comment", "com.apple.metadata:_kMDItemUserTags", or
   "Zone.Identifier").  Servers and clients MUST NOT normalize attribute
   names across platforms.  The server keeps an attribute that one
   platform writes, even where another platform has no equivalent for
   it.

   An attribute value whose bytes are valid UTF-8 MAY be a String
   holding that text.  Any other value MUST be a Binary value as defined
   in [JMAP-METADATA] (for example "com.apple.FinderInfo", a binary
   plist, or a resource fork).  The server returns a value in the form
   the client stored it.

   Attribute values are ordinary metadata: they count against the size
   limits and quota of [JMAP-METADATA], and are copied, shared and
   protected by the rules there like any other namespace value.  A
   server rejects an attribute too large for its limits with the errors
   [JMAP-METADATA] defines, so a large named stream such as a resource
   fork can only be stored where the server's limits allow it.

   Attributes shared with every reader of the node (for example a
   quarantine flag) are stored under "metadata".  Attributes private to
   the current user (for example that user's own tags) are stored under
   "privateMetadata" where the server supports it.

   Example — a textual attribute and a binary one:





Gondwana                   Expires 6 May 2027                  [Page 32]

Internet-Draft                JMAP FileNode                November 2026


   {
     "metadata": {
       "xattr": {
         "user.comment": "draft copy",
         "com.apple.FinderInfo": {
           "@type": "Binary",
           "base64": "VEVYVHR0eHQAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA="
         }
       }
     }
   }

   To set or remove a single attribute without disturbing the others, a
   client patches the path directly.  RFC 6901 escaping applies to any
   "/" or "~" in the attribute name ("/" as "~1", "~" as "~0"):

   [["FileNode/set", {
     "accountId": "u1",
     "update": {
       "f42": {
         "metadata/xattr/Zone.Identifier":
           "[ZoneTransfer]\r\nZoneId=3\r\n"
       }
     }
   }, "0"]]

   Setting an attribute's path to null removes it, following the
   "metadata" patch semantics of [JMAP-METADATA].

9.  Implementation Considerations

9.1.  Modification Timestamps

   Clients SHOULD provide an updated modified value when changing the
   content of a node.  This gives clients control over the timestamp,
   for example when preserving original modification times during file
   synchronization.  Clients that do not care about preserving
   timestamps can set modified to null to have the server use the
   current time.

   Renaming or moving a node does not change its modified time, as on
   common local filesystems.  A client SHOULD NOT include modified in an
   update that only renames or moves a node.

   Clients may also choose to update the modified timestamp on a parent
   directory when moving a child node in or out, to reflect that the
   directory's contents have changed.




Gondwana                   Expires 6 May 2027                  [Page 33]

Internet-Draft                JMAP FileNode                November 2026


9.2.  Timestamp Precision

   The UTCDate type (Section 1.4 of [JMAP-CORE]) supports fractional
   seconds.  Servers SHOULD include sub-second precision in created,
   modified, accessed, and changed timestamps where their storage
   backend supports it.  Clients MUST preserve fractional seconds when
   they send timestamps back to the server.

   A server MAY store timestamps with less precision than a client
   sends, down to whole seconds.  It then truncates the value it stores,
   and returns the stored value in FileNode/get, so a client can learn
   the precision in use.  Clients comparing a local time with a server
   timestamp (for example to recognize their own changes) need to allow
   for this.  Comparisons the server makes between timestamps use the
   stored precision.

9.3.  Filename Character Restrictions

   Servers should set forbiddenNameChars to include characters that are
   problematic for their storage backend and for the broadest set of
   clients, and may reject names that are problematic (see "name" in
   "Common Properties").

   The following characters are problematic on common platforms:

   *  Windows: <, >, :, ", \, |, ?, *, and control characters
      (U+0000-U+001F).  Windows also forbids trailing dots and spaces in
      names.

   *  macOS: : (HFS+ legacy; displayed as / in Finder).

   *  Linux: the null byte (U+0000).

   The following names are problematic:

   *  All platforms: . and .. (path traversal).

   *  Windows: reserved device names CON, PRN, AUX, NUL, COM0-COM9, and
      LPT0-LPT9.  These are reserved regardless of file extension (for
      example, "CON.txt" is also forbidden).

   A server targeting broad client compatibility should include at least
   /<>:"\|?* in forbiddenNameChars, and reject the names . and ...
   Clients that sync to platforms with further restrictions, such as the
   Windows reserved names, need to handle those names locally, since
   other clients may create them.





Gondwana                   Expires 6 May 2027                  [Page 34]

Internet-Draft                JMAP FileNode                November 2026


9.4.  Case Sensitivity

   Windows and macOS filesystems are typically case-insensitive
   (treating "Foo" and "foo" as the same name), while Linux filesystems
   are typically case-sensitive.  Clients syncing to case-insensitive
   platforms should use compareCaseInsensitively on FileNode/set
   requests to prevent creating sibling nodes whose names differ only in
   case, as these cannot coexist on the target platform.

9.5.  Access Time Updates

   Updating accessed on every file read generates significant API
   traffic for little value.  Clients are encouraged to use a "relatime"
   strategy similar to modern POSIX filesystems: only update accessed if
   the current value is older than modified, or if more than 24 hours
   have elapsed since the last accessed update.  Clients should batch
   access time updates with their next JMAP request rather than making a
   dedicated call.

10.  Security Considerations

   All security considerations from [JMAP-CORE] apply to this document.

10.1.  Path Traversal

   Clients that reconstruct filesystem paths from FileNode hierarchies
   MUST validate the resulting paths and reject any that would escape
   the intended directory tree.  Servers SHOULD include / in
   forbiddenNameChars and reject the names . and .. to prevent path
   traversal attacks via node names.  When extracting an archive into
   FileNodes, the server builds the tree itself, so it resolves every
   entry name relative to parentNodeId, even one with a leading "/", and
   treats entry names that could escape it as unsupported entries (see
   "Extracting Archives into FileNodes").

10.2.  Symlink Targets

   Symlink targets are not validated by the server to point to existing
   nodes.  Clients that resolve symlinks MUST guard against symlink
   loops (a symlink pointing to an ancestor of itself) and MUST NOT
   follow symlinks outside the FileNode tree.  Servers SHOULD impose a
   limit on the length of target values and MAY reject targets
   containing ".." path components.








Gondwana                   Expires 6 May 2027                  [Page 35]

Internet-Draft                JMAP FileNode                November 2026


10.3.  Denial of Service

   Deep nesting of FileNodes or very large numbers of children under a
   single parent can consume significant server resources.  Servers
   SHOULD enforce reasonable limits via maxFileNodeDepth and MAY impose
   additional limits on the number of children per node.  Recursive
   operations, such as destroying a subtree with onDestroyRemoveChildren
   or copying a Directory with FileNode/copy, can be expensive; servers
   SHOULD impose limits on the size of subtrees that can be destroyed or
   copied in a single operation.

10.4.  Access Control

   The discoverability rules defined in this document mean that ancestor
   nodes of shared content are visible (with mayRead false) to users who
   have access to descendants.  While these ancestor nodes do not expose
   file content, their names and structure may reveal information about
   the file hierarchy.  Server administrators and users sharing content
   should be aware of this.

   A user who can destroy a node, but cannot discover all of its
   descendants, can still learn that the node has children: the destroy
   fails with "nodeHasChildren", or with "forbidden" when
   onDestroyRemoveChildren is true.  Any failure reveals this.  The
   alternatives would be to reveal the ids of the hidden nodes, or to
   destroy data the user cannot see, and both are worse.

   Changes to the shareWith property on a node affect all descendants,
   and so does moving a node to a parent that is shared differently.
   Removing sharing from a parent node, or moving a subtree out of a
   shared Directory, makes those nodes undiscoverable to the affected
   users, unless a descendant is also shared with them directly, which
   may be surprising if those users had been actively working with the
   shared files.

10.5.  Extended Attributes

   Some extended attributes carry security meaning on the platform that
   reads them.  On Linux, "security.capability" grants capabilities to
   an executable, "security.selinux" sets its security label, and
   attributes under "trusted." and "system." (such as
   "system.posix_acl_access") change privileges or access control.
   Anyone with write access to a node can set these values, so a client
   that restores them lets that user change privileges on the client's
   machine.  Clients MUST NOT apply attributes whose names begin with
   "security.", "trusted." or "system." to local files unless explicitly
   configured to by the local administrator.




Gondwana                   Expires 6 May 2027                  [Page 36]

Internet-Draft                JMAP FileNode                November 2026


   Other attributes mark files as downloaded from an untrusted source,
   such as "com.apple.quarantine" on macOS and the "Zone.Identifier"
   stream on Windows, and the platform warns before such a file is
   opened.  A client that drops these markers when it syncs a file lets
   the file bypass that warning, so clients SHOULD preserve them.  A
   client SHOULD NOT treat the absence of a marker as evidence that a
   file is safe: any user with write access to the node can remove it.

10.6.  Content Security

   Servers that perform content scanning or malware detection SHOULD
   scan blobs referenced by FileNode objects.  The mediaType property is
   client-asserted and MUST NOT be trusted for security decisions;
   servers SHOULD independently verify content types where this matters.

   *  Removed the "newest" and "unchanged" values of onExists. "newest"
      compared client clocks and was easily mistaken for a content
      precondition.  "unchanged" duplicated, and conflicted with,
      [JMAP-CONDITIONAL]: to replace a node only if it is the one
      expected, a client destroys it and creates the replacement in one
      FileNode/set, with an "ifUnchangedBy" precondition on the destroy.
      [JMAP-CONDITIONAL] is now an informative reference.

   *  Creating or moving a node to the top level without
      mayCreateTopLevelFileNode fails with "forbidden".

   *  Direct HTTP Write PUT and PATCH set modified to the current server
      time.

   *  Direct HTTP Write accepts Repr-Digest and Content-Digest
      [DIGEST-FIELDS] on PUT and PATCH, rejecting a mismatch, and
      returns digests of the new content requested with Want-Repr-
      Digest.

   *  Fixed the blob capability name in the ArchiveEntry text to
      urn:ietf:params:jmap:blob2, matching [JMAP-BLOBEXT].

   *  Renaming or moving a node does not change its modified time; the
      guidance to update modified now applies to content changes.

   *  A server may store timestamps with less precision than clients
      send, down to whole seconds, truncating and returning the stored
      value.

   *  Direct HTTP Write digests use the algorithms listed in the
      supportedDigestAlgorithms capability of [JMAP-BLOBEXT], and
      clients use the first one they support.

   *  The "xattr" namespace maps an attribute name directly to its
      value: a String for UTF-8 text, or a [JMAP-METADATA] Binary value.
      Removed XattrValue and its "blobId", so attribute values are
      ordinary metadata and the metadata quota, copy and access rules
      apply to them.  Removed the maxDepth requirement, which was wrong
      under [JMAP-METADATA]'s depth rules.

   *  Added security considerations for extended attributes that grant
      privileges and for download markers.

   *  Direct HTTP Write returns 404 for a node that does not exist or is
      not discoverable, and mayModifyContent for a File is its parent's.
      The modified definition notes that Direct HTTP Write sets it.

   *  FileNode/get always returns @type, and omits requested properties
